# 后端性能与容量验证

本文记录本轮优化的并发边界、压测方法和适用范围。代码验证与隔离压测不等于生产环境已部署。本轮没有重启开发服务，没有修改其数据库。排行榜改用新集合，不迁移旧榜单；原生导航变更需重新编译，后端应正常关服保存后重启应用。

## 实现边界

- **单玩家共享队列**：客户端请求和会修改玩家状态的服务回调进入同一玩家队列。跨服务等待恢复后重新核对连接、玩家对象及相关流水号，旧连接和旧回调不能覆盖新状态。已接纳的后续回调（continuation）必须排空，不能在退出过程中提前撤销其执行资格。
- **保存确认后回收**：在线退出和离线回调收尾使用一次当前快照的保存屏障；先等待原保存锁及前序 ACK，再提交当前快照，确认后释放缓存。其他玩家在等待期间的新写留给后台，避免退出无限追写。调动和战果确认也在单玩家队列内使用当前快照屏障，仍先 ACK 再完成相关跨服务通知。关服仍在停止入口、排空已接纳工作后完整保存。失败保留数据及重试顺序，不能提前释放仍被排队工作引用的对象。
- **排行榜条目增量保存**：分数上报合并后异步发送；查询仍获取返回结果。脏状态和持久化更新细化到榜单条目，减少修改一名玩家时重写整张榜单的开销。
- **有界导航缓存**：地块占用索引代替逐城反查；默认最多缓存 4 份联盟导航，另有 1 份公共导航，`world_nav_cache_limit` 可配置为 1～32。淘汰时复用原生内存、差量修改权限格，但仍须全图重算连通性。它限制内存；超过缓存数量的联盟频繁轮转会增加 CPU 开销，不能据此保证吞吐提高。临时开放主城或关隘时禁止挂起、RPC 和重入，异常必须恢复阻挡与连通性。
- **活动行军集合**：世界帧只遍历正在移动的部队，暂停、等待、恢复、到达、回城和删除同步维护集合。世界帧同样禁止挂起和重入，失败后恢复 API、批量推送状态，并允许下一帧继续。
- **省去重复工作**：已初始化且位置不变的视野更新直接返回空差异；实体进入、离开仍由原事件链维护。原生 JPS 保留寻路算法，仅清理本次访问过的搜索槽位，不再每次清空整张百万格地图的父节点和开放集合数组。

这些约束是正确性边界，不应为了降低耗时而跳过保存确认、取消流水号检查或允许共享导航对象在临时修改期间挂起。本轮单元回归：**349 项通过**。

## 复现环境与命令

本轮测试机：Intel Core i7-12650H，WSL 可用 16 个逻辑线程、约 7.6 GB 内存。机器人、游戏进程、MongoDB 和 Redis 同机运行，因此结果同时受到压测端及共享机器资源影响。复测应保留实际 CPU、可用内存和配置记录。

在 WSL 的后端仓库根目录执行；需要已编译的 Skynet、本项目原生库，以及 Python 3、mongod、mongosh、redis-server：

~~~sh
python3 test/bench/run_capacity.py --users 1500,2000,3000 --duration 60 --ramp 30 --keep-going --verify-relogin
python3 test/bench/run_capacity.py --users 1500 --duration 180 --ramp 30 --verify-relogin
python3 test/bench/run_capacity.py --users 1500 --duration 60 --ramp 30 --account-model fresh --verify-relogin
~~~

脚本使用新建的独立数据目录和仅监听回环地址的端口。MongoDB 为 39027，Redis 为 39079；登录、网关和管理端口也与开发实例分离。端口占用时退出，不能改用开发库。结果、进程资源采样和日志保存在 build/capacity 下的本次运行目录。

上面的用户数是测试档位，不代表这些档位均已通过。默认在不达标后停止；第一条命令使用 --keep-going 继续收集过载档位，PASS 条件不会放宽。原始结果应随最终结论保存，不能只保留一行“最大在线人数”。

## 负载与计时

准备分两阶段：先全员完成注册、登录、资源及编队，再统一逐人验证真实行军路线，避免后创建的城市挡住先选的路线。只有全员路线有效才开始计时；无路仍判失败，准备阶段的候选拒绝单独记录。默认 super 模型预先补齐全部武将，测量重复武将转换和较大玩家文档；fresh 模型每档使用新账号，保持初始单武将，补充招募券及必要编队兵力，并核对抽卡新增武将及最终完整英雄集合。

每名玩家按固定计划每 500 ms 执行一次逻辑动作，玩家之间错开相位：

| 动作 | 比例 |
| --- | ---: |
| 行军与回城交替 | 10% |
| 十连抽卡 | 5% |
| 更新视野并查询行军列表 | 10% |
| 心跳 | 10% |
| 其它业务查询 | 65% |

“视野并查询”包含多条协议，因此逻辑动作率与网络消息率不同。名义动作率为玩家数乘以 2 次/秒。

同时记录发送到响应的耗时，以及从**计划发送时刻**到完成的 scheduled_latency。后一指标包含客户端发起迟到和积压，避免只等待上一请求完成再发下一请求的闭环模型掩盖过载。被跳过的计划时隙计入 missed，不能作为成功吞吐量消失。

## 通过标准

每档同时满足以下条件才通过：

- 所有账号准备完成并完成测试；运行失败、拒绝、超时及 missed 均为 0。
- scheduled_latency 的 P99 不超过 100 ms；每类实际请求各自的响应 P99 也须不超过 100 ms，防止总体分位掩盖少数操作的长尾。成功逻辑动作率至少达到计划动作率的 95%。普通响应 P99 不能替代包含发送迟到的计划延迟。
- 世界帧处理和调度迟到的 P99 上界均不超过 50 ms，世界帧错误为 0。
- 每次十连响应核对抽卡次数递增且奖励列表非空；随后在隔离 MongoDB 中逐人比对已确认的最终抽卡计数，不允许缺失或不一致。fresh 模型额外比对最终武将 ID 集合。
- 玩家退出后观察真实 agent 指标，玩家、武将、道具索引、队列、保存重试和后续回调计数均须归零；不能通过主动清理缓存制造通过结果。

世界帧 step_ms 使用 skynet.hpc 的单调时钟测量。P99 由固定直方图桶求上界；late_ms 使用 10 ms 粒度的调度时间，不能据此宣称亚毫秒调度精度。完整判断还应查看最大值、错误日志、CPU 和 RSS，不能仅凭平均值判断流畅。世界探针按整数秒截取近似测量窗口，存在约 1 秒边界误差；run_max_ms 是本次服务启动以来的最大值，可能包含准备阶段，不冒充当前档位的精确窗口最大值。

## 离线源码基准

以下是单进程、合成数据下的实际 Lua/C 模块基准，用于比较实现成本，**不是服务器同时在线容量结论**。

| 场景 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 1000 主城、24 联盟轮转，寻路 P99 | 315.7 ms | 24.4 ms |
| 同场景寻路 P50 | 1.208 ms | 6.966 ms |
| 同场景整个离线进程 RSS | 509.7 MiB | 115.3 MiB |
| 原生导航实例数（含公共图） | 25 | 5 |
| 10 万静态实体、100 支行军，世界帧 P99 | 13.17 ms | 0.80 ms |

联盟实验为两轮共 48 个样本，混合冷建与暖查询，且早于后续 JPS 缓冲优化。P50 上升说明缓存淘汰用部分轮转 CPU 换取有界内存，不能仅凭 P99 降低认定全面更快。原始 RSS 为 521968 KiB 与 118104 KiB。

复现当前实现：

~~~sh
skynet/3rd/lua/lua test/bench/bench_world_capacity.lua nav logic/service/world/module/map/mgr.lua 1000 24
skynet/3rd/lua/lua test/bench/bench_world_capacity.lua aoi logic/service/world/module/aoi/mgr.lua 100000 100
~~~

原生搜索缓冲补充对照：同一张 1000×1000 地图、同一批 2000 条短路径，总 CPU 耗时从 2386.230 ms 降到 1753.502 ms（下降 26.5%），P50 从 0.977 ms 降到 0.584 ms，P99 从 4.041 ms 到 3.987 ms。完整路径结果一致，P99 长尾仍主要受实际搜索影响。

进一步放大到 10000 主城时，首次导航分配仍出现超过 50 ms 的长尾；1000 支同步出发的平行同盟行军也观察到 GC 长尾。这些边界应保留在容量评估中，不能把固定缓存或活动集合解释为耗时硬上限。

## 实测结果

2026-11-09 的最终阶梯压测如下。每档计时 60 秒，4 个 agent、8 个游戏工作线程；机器人和 MongoDB/Redis 同机运行。

| 活跃账号 | 成功动作/秒 | 总请求 P99 | 计划延迟 P99 | 行军 P99 | 十连抽卡 P99 | 结论 |
| ---: | ---: | ---: | ---: | ---: | ---: | --- |
| 1500 | 3000.00 | 35.75 ms | 41.94 ms | 62.45 ms | 44.90 ms | PASS |
| 2000 | 4000.00 | 81.95 ms | 86.93 ms | 165.30 ms | 62.20 ms | FAIL：行军及资源查询单项超限 |
| 3000 | 5863.02 | 1200.24 ms | 1205.78 ms | 1495.34 ms | 401.33 ms | FAIL：明显过载 |

三档业务拒绝、超时、运行错误均为 0。3000 档有 8219 个计划时隙因迟到而未发出；这不是服务端丢弃 8219 个已发送请求，也不能计作成功吞吐。三档已确认抽卡次数逐人核库全部一致，分别完成 9000、12000、18000 次十连；退出后所有观察到的玩家缓存、队列、保存重试、后续回调计数均归零。额外顶号重连检查通过。

| 活跃账号 | 世界帧处理 P99 上界 | 世界调度迟到 P99 上界 | 游戏 CPU 均值 / 采样峰值 | 游戏 RSS 峰值 | Mongo CPU 均值 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 1500 | 20 ms | ≤10 ms（计时粒度） | 144.4% / 178.8% | 688.9 MiB | 10.1% |
| 2000 | 50 ms | 10 ms | 223.7% / 364.3% | 883.3 MiB | 14.0% |
| 3000 | 250 ms | 500 ms | 521.8% / 993.6% | 1418.9 MiB | 28.8% |

CPU 的 100% 表示占用一个逻辑核，峰值来自约 1 秒采样。世界执行/迟到的启动以来最大值分别为：1500 档 59.36/40.00 ms，2000 档 84.31/80.00 ms，3000 档 244.19/420.00 ms；包含各档之前的准备或低档阶段，不能作为精确测量窗口最大值。

补充回归记录：早期一轮 2000 人曾有 17 次行军业务拒绝，当时没有保存具体消息，因此该轮未通过验收，原因未确认。增加原因记录及成功后才切换往返状态后，最终三档均未复现，不能把它直接归因于数据库或容量。旧、新原生寻路对照及后续正式轮结果分开保存，不混用为同一轮测量。

延长确认：另起独立数据库，1500 个满武将账号持续 180 秒，540000 次操作全部成功，维持 3000 次/秒。总请求 P99 35.92 ms，计划延迟 P99 42.37 ms，行军 P99 63.47 ms，十连 P99 46.51 ms；拒绝、超时、missed 均为 0。27000 次十连的最终计数逐人核库一致，缓存全部归零，重登验证通过。行军单次最大 215.33 ms、十连最大 112.17 ms，故通过 P99 目标不等于承诺每次请求都没有延迟尖峰。世界执行 P99 上界 20 ms；游戏 CPU 均值 150.3% / 采样峰值 349.0%，RSS 峰值 687.3 MiB，Mongo CPU 均值 10.5%。

fresh 新武将链路：另起独立数据库，1500 个新账号持续 60 秒，180000 次操作全部成功，维持 3000 次/秒。总请求 P99 28.70 ms，计划延迟 P99 35.90 ms，行军 P99 51.39 ms（最大 83.80 ms），十连 P99 36.49 ms（最大 63.14 ms）。完成 9000 次十连，实际新增 11811 个武将；1500 个账号的抽卡次数与最终完整武将 ID 集合均与 MongoDB 一致，拒绝、超时、missed 为 0，退出缓存全部归零，重登验证通过。

当前可复述的结论是：**该机器、该固定相机且无联盟的混合负载下，1500 活跃账号通过短时阶梯、三分钟确认及新武将链路测试；2000 账号未通过逐协议延迟目标，3000 账号明显过载。** 这不是注册人数上限，也不是任意盟战或相机操作下的上线容量。三分钟确认不是长时间 soak test。

原始证据保存在各次 `build/capacity` 运行目录的 `results.json`、`metrics.jsonl`、`process-人数.jsonl`、`exit-status.json`；最终单元测试日志为 `build/capacity/final-unit-tests.txt`。所有隔离游戏、中心、数据库与机器人进程均已退出，独立端口已释放。生产代码与测试尚未提交或推送。

## 适用范围

尚未进行依赖持续无响应、进程强杀和断电的故障压测；不把正常 ACK 与可重试异常测试解释为跨文档事务或断电零丢失保证。对仍存活但持续不响应的依赖，不通过超时释放玩家锁让旧请求继续改写状态。

在线压测账号没有加入联盟，视野固定在本城。结果不能外推多联盟轮转、频繁移动镜头或集中攻城；上述联盟导航基准不能替代真实多联盟在线压测。该模型验证上述短时混合业务及其持久化结果，不覆盖长时间运行的内存稳定性或完整客户端渲染。它不测客户端 FPS，也不能直接推算任意玩法、任意机器配置下的承载人数。
